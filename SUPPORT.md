# Platform validation and support policy

The [README support table](README.md#platform-support) is the consumer-facing trigger contract. Linux and Windows are required release targets; macOS remains a candidate. Neither successful listener registration nor `process.emit('SIGINT')` proves OS integration.

## Matrix and evidence

`.github/workflows/platform-validation.yml` runs packed-package consumer tests on each of Linux (`ubuntu-latest`), Windows (`windows-latest`) and both macOS architectures: **ARM64** (`macos-latest`) and **Intel x64** (`macos-26-intel`). Every target runs Node **22.0.0, current 22.x, current 24.x and current 26.x**, giving eight dedicated macOS jobs. Each macOS job checks the actual Node architecture against its matrix target, so a runner-label change cannot silently omit an architecture. Node 22.0.0 tests the consumer minimum without installing development dependencies. Development checks run separately on Linux with Node 22.22.1, 24.x and 26.x. Odd-numbered and future Node versions are not individually validated; `engines.node` remains `>=22.0.0`.

Every job retains `platform-validation.log`, including the actual OS release, CPU architecture, Node version, each test and skip reason, as a workflow artifact. macOS artifact names include the architecture so ARM64 and Intel results remain separate. Runner image names describe CI coverage, not every Linux distribution, Windows release, macOS version or CPU architecture. Architectures not selected by these runner labels, service hosts, containers and unusual terminal hosts are not certified by these jobs. Consult the recorded host details and [GitHub's runner specifications](https://docs.github.com/en/actions/reference/runners/github-hosted-runners); both selected macOS runners currently cover macOS 26, not every older macOS release.

The `Linux and Windows support gate` requires every Linux/Windows matrix entry to succeed. Both npm publication and stable Pages deployment depend on this validation workflow after the build, and it downloads and tests the **same tarball** later published. A failing, skipped or cancelled required matrix blocks publication. A retry validates the original release archive again; no prior unrelated CI run substitutes for it.

The dedicated macOS jobs retain real failures but use `continue-on-error` while support is exploratory. Their failure does not relax the Linux/Windows gate or block those releases. **Promote macOS only after all eight dedicated jobs across ARM64 and Intel x64 pass on the intended revision**, record links to the run/artifacts, remove its `continue-on-error`, include it in the required support gate, and update the README table and this policy together. A green overall workflow is not proof that an exploratory macOS job passed.

Validation status on **6 October 2026**: Linux x64 packed-consumer validation passed on Node **22.0.0, 22.23.1, 24.18.0 and 26.10.0**. Repository checks passed on the development toolchains **22.22.1, 24.18.0 and 26.10.0**, and actionlint validated the workflow definitions. Native Windows and macOS validation cannot be executed in this Linux workspace and remain pending until their runners test these changes. There is no new unconditional macOS claim, and Windows native behavior is conditional on passing its required matrix. No release is authorized by this document.

## Test boundaries

- `npm run test:portable`: isolated child-process API, custom-event, error-strategy, timeout, handler-mutation and natural `beforeExit` tests. Listener bookkeeping tests can register signal names, but their synthetic dispatch checks only EventEmitter behavior.
- `npm run test:signals`: genuine OS integration. No `process.emit` sends a shutdown trigger in this suite. Fixtures record synchronous file markers so `process.exit()` cannot lose the evidence in buffered console output. Parents wait for readiness before delivering a trigger.
- `npm run test:runtime`: both suites. `npm run test:consumer` runs both through the packed package's public exports, including the native harness copied from `tests/`.

Linux/macOS use parent-delivered `child.kill` with an explicit allowlist: default `SIGINT`, `SIGTERM`, `SIGHUP`, and opt-in `SIGUSR2`. Tests check signal-specific cleanup, restoration of defaults, awaited phase order, real numeric exit status, a custom exit code, a hanging handler's deadline, repeatable non-terminating handling and no cleanup after `SIGKILL`. macOS uses its own real signal numbers rather than Linux constants.

Windows uses a PowerShell/C# harness calling `CreateProcessW(CREATE_NEW_CONSOLE)`, `AttachConsole` and `GenerateConsoleCtrlEvent`. Ctrl+C is sent to group zero inside the **isolated fixture console**, never the test runner's console; `CREATE_NEW_PROCESS_GROUP` is deliberately avoided because it disables Ctrl+C. The harness protects itself with a native control handler. Ctrl+Break validates opt-in `SIGBREAK`. `WM_CLOSE` closes the actual console window to validate short asynchronous `SIGHUP` cleanup. Native API errors, missing readiness, missing console windows or incomplete cleanup fail the tests; they are never silently skipped or replaced with emissions. The fixture is force-terminated and reaped on harness failure.

Separate Windows tests use `TerminateProcess`, `taskkill /F` and real `process.kill` emulation to assert that forced termination produces no cleanup markers. Linux/macOS `SIGKILL` and Windows `TerminateProcess` also interrupt a handler already running and verify that cleanup does not complete. Explicit `process.exit()` bypass is checked everywhere. These tests establish the limitations; forced termination is never a graceful trigger.

## Signal exclusions and skip reporting

The old blanket enumeration of `os.constants.signals` has been replaced by the allowlist and native Windows cases above. `tests/signal-policy.js` gives a reason to **every excluded signal present on the current platform**, and the suite reports each as a named skip. Opposite-platform integration cases also state exactly which native mechanism they require. There are no capability-probing skips that turn a required native test failure into a pass.

## Remaining gaps

Windows/macOS runner evidence is required before claiming native success. Console closure only verifies cleanup that fits within the OS deadline; it cannot guarantee completion of slow cleanup. Windows services do not automatically deliver console events, and this package installs no service-control handler. Terminal raw mode and external supervisors can prevent or interrupt delivery. Forced termination, crashes and suspended processes cannot be made graceful by this API.

The API remains unchanged: defaults are `SIGTERM`, `SIGHUP`, `SIGINT`, `beforeExit`; Windows `SIGBREAK` is explicit opt-in. Unsupported names can remain custom EventEmitter events, so `listSignals()` is a list of registrations, not OS capabilities. `addSignal()` now attaches its listener before changing its registry, so failed native attachment leaves no phantom active signal and a later retry can succeed.

Native behavior references: [Node signal events](https://nodejs.org/docs/latest-v22.x/api/process.html#signal-events), [GenerateConsoleCtrlEvent](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent), [SetConsoleCtrlHandler](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler), and [libuv Windows signal dispatch](https://github.com/nodejs/node/blob/v22.0.0/deps/uv/src/win/signal.c).
